## 4. 指摘事項一覧

### 4.1 重大度「高」

#### 指摘1: バリデーションエラー時のメッセージが設計書の日本語メッセージと一致せず、フロントエンドの型前提とも形状が食い違っている

- 観点: バグ・不具合/設計整合性
- 該当箇所:
  - `backend/app/schemas/invoice.py:10-12`、`backend/app/schemas/expense.py:9`、`backend/app/schemas/client.py:9`、`backend/app/schemas/company_profile.py:9`、`backend/app/schemas/payment.py:6` ほか、Pydantic `Field(..., description="...")` で日本語エラーメッセージを定義している全箇所
  - `frontend/src/api/client.ts:7-9`(`ApiErrorBody.detail?: string`という型定義)
  - `frontend/src/components/ItemsEditor.tsx`・`frontend/src/pages/InvoiceDetailPage.tsx`・`QuoteDetailPage.tsx`・`ExpenseFormPage.tsx`(保存前のクライアント側入力チェック・保存ボタンの活性制御がほぼ無い)
- 内容:
  Pydanticの`Field(gt=0, description="数量は0より大きい数値で入力してください")`のような書き方は、`description`がOpenAPIスキーマ用のメタデータとして扱われるだけで、実際のバリデーションエラーメッセージにはならない。実機確認したところ、`gt=0`違反時には`"Input should be greater than 0"`のような英語の定型メッセージが返る。

  さらに、FastAPI(Pydantic v2)のバリデーションエラーは自動的にHTTP 422となり、レスポンスボディは`{"detail": [{"type": ..., "loc": [...], "msg": ...}, ...]}`という**配列**形式になる。今回実際に`POST /api/clients`へ`{"name": ""}`を送信して確認したところ、次のレスポンスであった。
  ```
  HTTP 422
  {"detail":[{"type":"string_too_short","loc":["body","name"],"msg":"String should have at least 1 character","input":"","ctx":{"min_length":1}}]}
  ```
  一方、フロントエンドの`ApiErrorBody`型は`detail?: string`という前提であり、`extractErrorMessage()`はこの配列をそのまま文字列として画面の`<Alert>{errorMessage}</Alert>`等に渡してしまう。Reactは文字列・数値以外のオブジェクト(配列の要素であるオブジェクト)を子要素としてそのまま描画できないため、実行時エラー(`Objects are not valid as a React child`)により当該画面の描画が破綻する可能性が高い(本レビューでは実ブラウザでの再現までは行っていないが、Reactの既知の挙動から強く推定される)。

  この422応答パスは、単なる「不正な直接API呼び出し」でしか到達しない想定外ケースではない。`ItemsEditor`の数量・単価入力欄には`保存`ボタンの活性制御や入力時バリデーションがなく(入金額入力欄のみ`disabled`制御あり)、ユーザーが数量欄を空にして保存する(→`Number('')`で`0`扱いになり`gt=0`違反)といった、通常操作の範囲内で再現しうる。詳細設計書3.3章・8章で定義された「数量/単価は0より大きい数値で入力してください」等のメッセージが、実際には一度も画面に表示されない設計になっている。
- 推奨対応:
  1. Pydanticスキーマ側は`field_validator`で独自例外(`ValidationFailedError`など、400番台・文字列detailを返す既存の仕組み)に変換するか、FastAPI側で`RequestValidationError`用のカスタム例外ハンドラを追加し、`detail`を設計書どおりの日本語文字列(または少なくとも一貫した形式)で返すようにする。
  2. フロントエンド側でも、配列形式の`detail`が来た場合の防御的な処理(先頭要素の`msg`を使う、または汎用メッセージにフォールバックする等)を`extractErrorMessage()`に追加する。
  3. 併せて、主要な入力項目(数量・単価・金額等)についてはクライアント側でも保存前チェック・ボタン活性制御を入れ、詳細設計書3章の「未入力時のエラー表示」要件を満たすことを推奨する。
- 対応状況: **対応済み**(reviewer検証: 2026-09-16、版数1.1)
  - `git diff`で`backend/app/main.py`に`handle_request_validation_error`(422応答を単一文字列`detail`に整形)を追加していること、`invoice.py`・`expense.py`・`client.py`・`company_profile.py`・`payment.py`の主要フィールドに`field_validator(mode="before")`が追加されていることを確認した。
  - 実機で`POST /api/clients`に`{"name": ""}`を送信し、`HTTP 422 {"detail":"名称を入力してください"}`という単一文字列応答であることを確認した(配列形式ではないことを確認)。
  - `backend/tests/test_main.py`(名称未入力・数量0・単価0・金額0の4ケース)、`frontend/src/api/__tests__/client.test.ts`(配列/文字列両形式の`extractErrorMessage()`)を実際に読み、意味のあるassertになっていることを確認した。
  - `ItemsEditor.tsx`の`validateItems()`・`InvoiceDetailPage.tsx`/`QuoteDetailPage.tsx`の保存ボタン活性制御(`clientId === null || !!itemsErrorMessage`)・`ExpenseFormPage.tsx`の`isSaveDisabled`を確認した。`frontend/src/pages/__tests__/InvoiceDetailPage.test.tsx`(品目明細を全て削除すると保存ボタンが無効化される)・`ExpenseFormPage.test.tsx`(金額未入力時に保存ボタンが無効化される)のテストで実際に検証されている。
  - pytest 127件・Vitest 26件を再実行し全件成功、`tsc -b`もエラー無しであることを確認した。
  - 主要フィールド以外(例: 請求書の`due_date`の型不正等)は英語の定型メッセージが残るが、`detail`が常に単一文字列である点は担保されており、当初指摘した「Reactの描画が破綻しうる」リスクは解消されている。この限定対応であること自体はdeveloperの申告どおりであり、事実と相違ない。

#### 指摘2: 経費領収書アップロードのファイル名がサニタイズされておらず、パストラバーサル(CWE-22)が成立しうる

- 観点: セキュリティ
- 該当箇所: `backend/app/services/attachment_service.py:24-30`(`AttachmentService.save()`)、呼び出し元 `backend/app/routers/expenses.py:69-83`
- 内容:
  `save()`は次の実装になっている。
  ```python
  def save(self, expense_id: int, filename: str, content: bytes) -> str:
      expense_dir = self.base_dir / str(expense_id)
      expense_dir.mkdir(parents=True, exist_ok=True)
      stored_name = f"{uuid.uuid4()}_{filename}"
      file_path = expense_dir / stored_name
      file_path.write_bytes(content)
      return f"{expense_id}/{stored_name}"
  ```
  `filename`(アップロード時のファイル名、`multipart/form-data`のフィールド値としてクライアントが自由に指定可能)に対する検証が拡張子チェック(`validate()`)のみであり、パス区切り文字(`/`)や`..`を含むファイル名がそのまま`Path`結合に使われている。Pythonの`pathlib`は`/`演算子の右辺文字列にパス区切りが含まれていると、それを複数のパス構成要素として解釈するため、意図した保存先ディレクトリの外へファイルを書き込める。

  再現実験(一時ディレクトリ内、本番環境への書き込みは行っていない):
  ```python
  >>> from pathlib import Path
  >>> base = Path('/tmp/expense_dir/5')
  >>> stored_name = 'uuid1234_' + '../../../../tmp/evil.txt'
  >>> (base / stored_name).resolve()
  PosixPath('/private/tmp/tmp/evil.txt')
  ```
  ブラウザの`<input type="file">`は通常`File.name`にディレクトリ部分を含めないため、通常のブラウザ操作だけでは顕在化しにくい。しかし本APIは認証なし・入力検証もこの箇所だけが抜けており、同一Mac上の他プロセス・スクリプトから`curl`等で直接`POST /api/expenses/{id}/attachment`を呼び出せば、実行ユーザー権限で任意パスにファイルを書き込める。保存された相対パスは`expenses.attachment_path`にそのまま記録されるため、`GET /api/expenses/{id}/attachment`側にも同じ問題が波及する(サーバーが書き込んだパスを読み出すだけなので直接の外部入力にはならないが、書き込み時点の脆弱性がそのままデータとして永続化される)。
- 推奨対応: 保存時に`Path(filename).name`でファイル名部分のみを取り出す、または`/`・`..`・NULLバイト等を拒否する検証を追加する。`AttachmentService.validate()`にこのチェックを統合するのが望ましい。あわせて、`test_attachment_service.py`・`test_api_expenses.py`にパストラバーサル拒否のテストケースを追加することを推奨する。
- 対応状況: **対応済み**(reviewer検証: 2026-09-16、版数1.1)
  - `git diff`で`AttachmentService._validate_filename()`(`/`・`\`・`..`・NULLバイト・空文字を拒否)と`save()`側の`Path(filename).name`による多層防御を確認した。
  - 実機で、`POST /api/expenses/{id}/attachment`に`filename="../../../../tmp/pwned_review.jpg"`を指定したmultipartリクエストを送信し、`HTTP 400 {"detail":"対応していないファイル形式、またはサイズが上限(10MB)を超えています"}`で拒否されること、および意図した保存先ディレクトリ外(`/tmp/pwned_review.jpg`)にファイルが作成されないことを確認した。
  - `backend/tests/test_attachment_service.py`(`../../etc/passwd.jpg`・`../evil.png`・`sub/dir/receipt.jpg`・`..\evil.jpg`等のパラメタライズドテスト、`save()`が保存先ディレクトリの外に書き込まないことを確認するテスト)・`test_api_expenses.py`のテストを実際に読み、意味のあるassertになっていることを確認した。
  - pytest 127件を再実行し全件成功した。当初の指摘(CWE-22パストラバーサル)は解消されている。

### 4.2 重大度「中」

#### 指摘3: 予期しない例外(500系)がログ出力なしに握りつぶされ、障害調査ができない

- 観点: バグ・不具合/設計整合性
- 該当箇所: `backend/app/main.py:39-44`(`handle_unexpected_error`)
- 内容: `@app.exception_handler(Exception)`が全ての未捕捉例外を受け取り、固定文言のJSONResponseを返すのみで、`logging`モジュールの利用箇所がバックエンド全体に一つも無い(`grep`で確認済み)。FastAPIの例外ハンドラでExceptionを捕捉すると、Starletteの標準エラーログ出力(トレースバックのログ記録)より先に処理が完結してしまうため、実際に不具合が発生してもサーバー側のログに痕跡が残らない。
  基本設計書7章は「ログ: Uvicornの標準アクセスログ・エラーログのみとし、監査ログ等の特別な仕組みは設けない」としており、標準エラーログは最低限の障害調査手段として期待されている。また詳細設計書4.7.3章・`launch.sh`のエラー通知文言「起動に失敗しました。logs/uvicorn.logを確認してください」も、ログファイルに有用な情報が残る前提になっている。EIAI TEC本人は非エンジニアであり、原因不明のエラーが起きた際にログさえ残っていない状況は、保守運用上のリスクが大きい。
- 推奨対応: `handle_unexpected_error`内で`logging.exception(...)`等により、発生した例外のトレースバックをUvicornの標準エラー出力(`logs/uvicorn.log`)に記録するよう修正する。

- 日本語化: ハンドラは`errors[0]`のみを参照し、`loc`から文字列要素のみを抽出して最後の要素を項目名とするため、リスト内要素(`items.0.item_name`)・ネストしたlocでも正しく項目名が取れ、`KeyError`は発生しない(`.get`使用、`ctx`欠落もNoneで安全)。既存の日本語メッセージ(`Value error, `除去)は`_localize_standard_error`が`missing`・`string_too_long`のみを対象とするため壊れない。ボディ全体が空(`loc`が`body`)は汎用文言にフォールバックする。応答に入力値(`input`)は含まれず、情報漏えいのリスクは無い。項目名対応表は画面ラベル(取引先の「名称」、設定の「氏名」、案件の「案件名」「納期」、入金の「入金額」ほか)と一致している。
