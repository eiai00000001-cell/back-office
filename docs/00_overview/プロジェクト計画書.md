## 2. 案件概要

### 2.1 クライアント情報

- EIAI TEC(個人事業主本人)。本システムはEIAI TEC本人が事務作業に自ら利用する自分専用ツールである(企画書 1.3)。

### 2.2 依頼の背景・経緯

- 個人事業(EIAI TEC)における請求書発行・経費管理・見積書作成・財務管理・確定申告対応・契約書管理・経営管理など、複数の事務業務をホーム画面から選択して行える形に一元管理したいという要望が出発点(企画書 1.1)。
- 本システムはEIAI TECの「ポートフォリオ=業務基盤」戦略の中核ツールと位置づけられており、実業務での利用に加えて、AI駆動開発の実績としてGitHub公開も想定されている(企画書 1.2)。
- 企画書の段階では計15機能をTier1〜Tier3および横断機能に分類し、段階分けせず1つの統合ツールとして企画されていたが(企画書 1.2、2章)、ヒアリングの結果、開発は複数回のイテレーションに分けて段階的に進める方針とし、初回イテレーション(イテレーション1)ではTier1のうち5機能に絞って着手し、計画から納品までを完了した。
- イテレーション2では、企画書Tier2の#4「財務ダッシュボード」(企画書では概要「TBD」)を対象として、イテレーション1で構築済みの請求書発行・経費管理・見積書作成・見積→請求の自動変換・入金/売掛金管理の各データを集計・可視化する機能を追加する(2026-09-16ヒアリング結果)。

## 3. 目指すゴール

- 請求書発行・経費管理・見積書作成・見積から請求への変換・入金や売掛金の管理といった、お金の流れに直結する事務作業を1つのシステム上で行えるようにし、日々の事務負担を軽減する(企画書 1.1、2章)。
- 将来的には案件管理や財務ダッシュボードなどの機能も含めた統合ツールへと拡張していく構想があるが(企画書 1.2、2章)、初回イテレーションではまず「お金の流れを止めない・管理する」ための中核機能を確実に使える状態にすることを目指した。
- イテレーション2では、イテレーション1で蓄積されたお金の流れに関するデータ(売上・入金・経費・見積)を1つの画面で俯瞰できるようにし、日々の事務作業だけでなく、経営状況の把握・振り返りにも活用できる状態を目指す(2026-09-16ヒアリング結果)。

## 4. 進め方

### 4.1 フェーズ構成

本プロジェクトは以下の6フェーズで進める。各フェーズの成果物は`docs/`配下の番号付きフォルダに格納する。

| フェーズ | 確定させること |
|---|---|
| 計画 | 案件全体の目的・大枠のやること/やらないこと・前提/制約/リスク(本書) |
| 要件定義 | 対象機能ごとの詳細な要件・仕様(要件定義書.md、機能仕様書.md) |
| 設計 | 画面・データ構造・処理方式などの具体的な設計(基本設計書.md、詳細設計書.md、モックアップ) |
| 実装 | 設計に基づくプログラム実装 |
| テスト | 実装内容が設計・要件どおり動作することの検証 |
| 納品 | 成果物一式の取りまとめ、操作マニュアルの整備 |

- 初回イテレーション(本書が対象とする範囲)は、計画から納品までを上記6フェーズでウォーターフォール的に一気通貫で進める。
- 2回目以降の機能追加(Tier2・Tier3・横断機能など)は、同じ6フェーズを1機能または1グループ単位でアジャイル的にループさせながら進める想定である。

### 4.2 初回イテレーションの実装順序の目安

- ヒアリングにより、初回イテレーション対象の5機能の間で優先順位が示されている。
  - 最優先: 請求書発行、経費管理
  - 次点(必須だが優先度はやや下): 見積書作成、見積→請求の自動変換、入金・売掛金管理
- この優先順位は、要件定義以降のフェーズにおける詳細化・実装順序の目安として扱う。5機能すべてを初回イテレーションのスコープに含める点は確定事項であり、優先順位に基づいてさらに細かくフェーズを分けるかどうかは、要件定義フェーズでanalystが機能仕様を踏まえて判断する。

### 4.3 想定スケジュール

- 外部クライアント向けの納期制約はなく、EIAI TEC本人のペースで進める想定である(ヒアリング結果)。一次情報上、具体的な期日・マイルストーンの指定はない。

### 4.4 イテレーション2の位置づけ

- イテレーション1で計画から納品までの6フェーズを一気通貫(ウォーターフォール)で完了させたのを受け、イテレーション2は4.1で示したアジャイル的ループの2周目にあたる。財務ダッシュボード機能1つを対象に、同じ6フェーズ(計画→要件定義→設計→実装→テスト→納品)を再度回す(2026-09-16ヒアリング結果)。
- 本書はイテレーション2の「計画」フェーズの成果物であり、本書の内容を踏まえて要件定義フェーズでanalystが財務ダッシュボード機能の詳細要件(表示項目の具体的なレイアウト、グラフの種類、集計ロジックの詳細等)を確定する。
- イテレーション2で扱わない企画書Tier2の残り機能(経営管理、案件・プロジェクト管理、リマインダー/通知、レポート出力)およびTier3機能は、イテレーション3以降に持ち越す予定であり、具体的な着手順は今後のヒアリングで確定する(「5.2 やらないこと・対象外・将来検討」参照)。

## 5. やること/やらないこと

機能ごとの詳細な要件・仕様は本書では定めず、要件定義フェーズでanalystが要件定義書・機能仕様書として確定する。

### 5.1 対象機能

#### イテレーション1(完了)

- 企画書のTier1に分類された5機能のうち、以下5機能を初回イテレーションの対象とした(ヒアリング結果)。
  1. 請求書発行(最優先)
  2. 経費管理(最優先)
  3. 見積書作成(次点)
  4. 見積→請求の自動変換(次点)
  5. 入金・売掛金管理(次点)
- 上記5機能をEIAI TEC本人がローカル環境で利用できる状態にするための、必要最小限のホーム画面・共通UI(各機能への導線)を含む(企画書 1.1「ホーム画面から選択して行える形」、3章)。
- 技術スタック(Python+React+SQLiteによるローカル完結環境)の構築は、上記5機能を動かすための基盤として初回イテレーションのスコープに含んだ(ヒアリング結果)。

#### イテレーション2(今回対象)

- 企画書Tier2の#4「財務ダッシュボード」(企画書では概要「TBD」)を対象とする(2026-09-16ヒアリング結果)。
- 表示したい内容として、以下4点が挙がっている(複数選択、2026-09-16ヒアリング結果)。
  1. 売上・入金状況の可視化(イテレーション1で実装済みの請求書発行・入金管理データを集計)
  2. 経費の可視化(イテレーション1で実装済みの経費管理データを、勘定科目別・月別等で集計)
  3. 損益(収支)の可視化(売上と経費を突き合わせた収支状況)
  4. 見積の状況可視化(見積書の件数・金額・成約率など)
- 期間・粒度は月次中心(月単位での集計・グラフ表示を基本とする)とする。個人事業の事務管理として一般的な粒度との考えによる(2026-09-16ヒアリング結果)。
- 見積の成約率は、「見積→請求の自動変換」機能(イテレーション1で実装済み)により変換された件数 ÷ 見積作成件数、で算出する(2026-09-16ヒアリング結果)。
- データソースは全てイテレーション1で実装済みの各機能(請求書発行、経費管理、見積書作成、見積→請求の自動変換、入金・売掛金管理)のデータであり、新規のデータ入力機能ではなく既存データの集計・可視化・分析が中心となる見込みである(2026-09-16ヒアリング結果)。
- 表示項目の具体的なレイアウト・グラフの種類・集計ロジックの詳細は本書では定めず、要件定義フェーズでanalystが確定する。

### 5.2 やらないこと・対象外・将来検討

- 企画書のTier2に分類された機能のうち、財務ダッシュボードを除く以下4機能は今回(イテレーション1・2とも)対象外とし、将来イテレーションで扱う(企画書 2章、ヒアリング結果)。
  - 経営管理
  - 案件・プロジェクト管理
  - リマインダー/通知
  - レポート出力
- 企画書のTier3に分類された以下4機能は今回対象外とし、将来イテレーションで扱う(企画書 2章、ヒアリング結果)。
  - 確定申告対応
  - 契約書テンプレート
  - 顧客管理(簡易CRM)
  - レシート/領収書OCR取込
- 横断的に対応するとされていたデータバックアップ/エクスポート機能も、今回は対象外とし将来イテレーションで扱う(企画書 2章、ヒアリング結果)。企画書では「初期段階から組み込む基盤機能」と位置づけられていた点との差分であり、5.2の対象外化に伴う運用上の留意点は「7. リスク・懸念事項」に記載する。
- マルチユーザー対応・外部公開を前提としたアカウント管理や権限設計は、EIAI TEC本人専用利用という前提のため行わない(ヒアリング結果)。
- イテレーション2では、財務ダッシュボードに新たなデータ入力・編集機能(例: ダッシュボード画面からの請求書・経費の直接編集)は持たない。あくまで既存データの参照・集計・可視化にとどめる(2026-09-16ヒアリング結果)。

## 6. 前提・制約

- 利用者: EIAI TEC本人のみ。他者との共同利用や外部提供は想定しない(ヒアリング結果)。
- データ保存: ローカル完結。クラウド同期は行わない(企画書 1.3、ヒアリング結果)。
- 技術スタック: バックエンドPython、フロントエンドReact、ローカルDBにSQLiteを使用することで確定している(ヒアリング結果)。企画書1.3・5章で「要確認」「未確定」とされていた技術方針は、本ヒアリングにより確定した。
- 納期・体制: 外部クライアント向けの納期制約はなく、EIAI TEC本人のペースで進める(ヒアリング結果)。開発体制については、本プロジェクトの開発フロー(計画→要件定義→設計→実装→テスト→納品を各フェーズ専任のサブエージェントが担当する方式)に沿って進行する。
- 予算: 一次情報・ヒアリング結果に明示的な記載なし。自分専用ツールの開発という性質上、外部発注のような金銭的予算制約は想定されにくいが、念のため「8. 要確認事項」で確認する。
- 財務ダッシュボード(イテレーション2)のデータソース: 新規のデータ入力機能ではなく、イテレーション1で実装済みの請求書発行・経費管理・見積書作成・見積→請求の自動変換・入金/売掛金管理の各機能が保持するデータを集計・可視化する前提である(2026-09-16ヒアリング結果)。そのため、ダッシュボードの表示内容の正確性は、元データとなるイテレーション1側の入力データの網羅性・正確性に依存する。

## 7. リスク・懸念事項

- データバックアップ/エクスポート機能(企画書Tier15)は今回のイテレーションでは対象外となったため、初回イテレーションで構築するローカルDB(SQLite)のデータについて、開発・運用初期の期間中はバックアップ手段がない状態となる。データ消失時の影響とその間の運用方法について、事前に留意が必要である。
- 請求書発行・経費管理は税務(消費税・インボイス制度対応・勘定科目区分など)に関わる可能性がある業務領域だが、企画書上は各機能の詳細概要が「TBD」のままであり、法令対応の要否・範囲が未確定である。要件定義フェーズで具体化しないまま設計・実装に進むと手戻りが発生するおそれがある。
- 見積→請求の自動変換は、見積書作成機能・請求書発行機能の両方とデータ・仕様面で密接に連携する。3機能のデータモデル(項目構成、単価・税区分の引き継ぎ方など)の整合性を要件定義・設計の早い段階ですり合わせておく必要がある。
- 企画書のホーム画面(共通UI)構想は「TBD」のままであり(企画書3章)、初回イテレーションで最小限の画面構成にとどめた場合、将来機能追加時に画面構成の見直し・作り直しが必要になる可能性がある。
- 財務ダッシュボード(イテレーション2)は、請求書発行・経費管理・見積書作成・見積→請求の自動変換・入金/売掛金管理という5つの既存機能のデータを横断的に集計する機能であるため、各機能のデータモデル(勘定科目の区分方法、日付・金額の記録単位、見積・請求のステータス管理方法など)の間で表記揺れや粒度の不一致があると、集計結果の正確性・整合性に影響するおそれがある。要件定義・設計フェーズで、各データソースの実際の項目構成を確認したうえで集計ロジックを設計する必要がある。
- イテレーション1で入力・蓄積されたデータ量やデータ期間が少ない場合、月次グラフ等の表示が期待どおりの見え方にならない可能性がある(例: 運用開始間もない月のみのデータでは推移比較ができない)。テストフェーズでは実データに近いボリュームでの表示確認が望ましい。
- 損益(収支)の可視化は、売上(請求書・入金データ)と経費データを突き合わせる機能であり、両者の対象期間・計上基準(発生主義か現金主義かなど)が揃っていないと、数値の意味づけに誤解が生じるおそれがある。要件定義フェーズで計上基準の考え方を確認しておく必要がある。
