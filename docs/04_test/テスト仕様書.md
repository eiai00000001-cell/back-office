## 3. テスト観点

| # | 観点 | 定義 |
|---|---|---|
| 1 | 機能テスト | 詳細設計書の画面詳細設計・処理フロー・API/インターフェース設計どおりに動作するか(機能ID単位) |
| 2 | 異常系・入力値検証 | エラーハンドリング設計(詳細設計書8章)どおりに異常系が処理されるか |
| 3 | データ整合性 | DB詳細設計(詳細設計書6章)どおりにデータが登録・更新・参照されるか |
| 4 | 回帰確認 | フォローアップ時、既存の合格項目が新規修正で崩れていないか(初版では該当なし) |
| 5 | 機能横断・結合確認 | 複数機能にまたがる画面遷移・データの受け渡し等、単体テスト・機能単位レビューでは見えない不整合がないか(F-03→F-04→F-01→F-05の一連の業務フロー、ホーム画面のサマリー算出とF-05判定ロジックの整合等) |

### 3.1 機能ID単位の適用方針

- F-01〜F-06および共通機能それぞれについて、観点1(機能テスト)・観点2(異常系)を基本の適用対象とする(イテレーション1で適用済み、方針変更なし)。
- F-01・F-02・F-03の金額計算はDB保存値の検算(観点3)を必須とする。
- F-04(見積→請求変換)・F-05(入金・売掛金管理)・F-06(ホーム画面サマリー)は、他機能のデータに依存して算出される派生値が多いため、観点5(結合確認)を重点的に適用する。
- 起動.app/終了.appは、単体スクリプト実行(developer済み確認)に加えて実際の`.app`バンドル起動(観点1・5)を重点的に確認する。
- **F-07(財務ダッシュボード、イテレーション2追加)**: 読み取り専用機能で、書き込み系の異常系(バリデーションエラー等)を持たないため、観点2は「区画ごとのAPI障害時のエラー表示分離」(詳細設計書4.8.6章)・「見積成約率0件時のnull返却」(4.8.5章)の2点に限定して適用する。F-01(売上)・F-02(経費)・F-03/F-04(見積・変換)・F-05(入金)の既存データを月次集計する性質上、複数機能のデータが単一画面に統合される典型的な結合確認(観点5)機能であるため、観点5を最重点で適用する。観点3(データ整合性)は、DB上の生データとAPIレスポンスの集計値の突合(発生主義での計上基準・0円/0件補完・除外条件)を重点確認する。

## 4. テスト方針・実施方法

### 4.1 実施方法の区分

| 区分 | 内容 |
|---|---|
| 実機確認(バックエンドAPI) | 本番相当構成(`npm run build`→`uvicorn app.main:app`)でサーバーを実際に起動し、`curl`によるHTTPリクエストで全APIエンドポイントを実行し、レスポンス内容(ステータスコード・JSON本体)およびSQLite上のデータを検証する。 |
| 実機確認(.app起動・終了) | `dist/起動.app`・`dist/終了.app`をmacOSの`open`コマンドで実際に起動し(Finderでのダブルクリックと同一のLaunch Services経由の起動)、実ブラウザのHTTPアクセスログ・プロセス起動状況・PIDファイル・`osascript`通知ダイアログの実際の表示有無を確認する。イテレーション1で確認済み・解消済みのため、イテレーション2では再実施しない(2.3節参照)。 |
| 実機確認(SPA読み込み・ブラウザ自動操作、イテレーション2で拡充) | Playwright(Python、Chromium)を用いて実ブラウザで`http://127.0.0.1:8000/`にアクセスし、ホーム画面(SC-01)からのリンククリックによるSC-12への画面遷移、グラフ描画内容(区画見出し・合計金額・見積成約率等のテキスト)、フルページスクリーンショットによる目視確認を行う。あわせて、Playwrightのネットワークルーティング機能(`page.route`)で`/api/dashboard/*`の特定1本のみを意図的に500エラーに差し替え、区画ごとのエラー表示分離(4.8.6章)を実ブラウザ上で検証する。 |
| 静的確認 | フロントエンド実装コード(`frontend/src/pages/`・`components/`)を詳細設計書3章の画面詳細設計・mockups(SC-01〜SC-12)と突き合わせ、画面遷移・入力項目・バリデーション・表示ロジックの実装内容を確認する。UI操作結果そのものの実機確認ができない項目を補完する位置づけとし、単独では合格根拠としない。 |
| 参照確認 | README.md「5. テスト実行結果」(pytest 149件・Vitest 37件)、レビュー結果報告書.md 4章・8章の指摘対応状況を参照し、重複再実行はしない。 |

### 4.2 合否判定基準

- 期待結果(テストケース.mdに記載)と実施結果が一致した場合を「合格」とする。
- 詳細設計書・機能仕様書に明記された仕様との不一致、または実行時エラー・データ不整合が確認された場合を「不合格」とし、再現手順・実際の結果を記録する。
- README.md「6. 詳細設計書との差異」に記載済みの差異は仕様確定事項として扱い、原則不合格としない。ただしその差異どおりに実際に動作しているかは実機確認する。
- テスト実施中に、詳細設計書とmockupsとの間、または詳細設計書内の章同士の間で軽微な記載の不整合が見つかった場合(実装への影響がないもの)は「要確認事項」として記録し、不合格扱いとはしない。
- 実機確認の手段がない項目は「未実施」とし、代替として実施した静的確認・参照確認の内容を明記する。

### 4.3 F-07向けの追加方針(境界値・実データ検証)

- 詳細設計書4.8章の集計ロジックは、SQLの`WHERE`句による日付範囲絞り込みと`strftime`による月グルーピングを組み合わせているため、期間境界(`date_from`前日のデータが正しく除外されるか)を境界値テストとして重点確認する。
- F-04(見積→請求変換)直後で`issue_date`がNULLの請求書(詳細設計書4.4章)が、F-07の月次売上集計から正しく除外されることを、実際にF-04変換を経由したデータで確認する(F-04とF-07の結合確認)。
- 見積成約率(4.8.5章)は、0件時のnull返却(0除算回避)に加え、変換済み・未変換が混在するケースでの按分計算(小数第1位以下の丸め表示)も実データで確認する。
- 損益(収支)の黒字/赤字視覚化(基本設計書4.13章)は、赤字月を意図的に作成し、実際に配色が切り替わることをスクリーンショットで確認する。

### 4.4 回帰確認方針(イテレーション2)

- F-07実装に伴うF-01〜F-06・共通機能への影響は、既存の`Invoice.issue_date`・`Quote.issue_date`・`Payment.payment_date`へのインデックス追加(詳細設計書6.4章)のみであり、テーブル定義・カラム定義・既存API・既存画面のコードは変更されていないことをreviewerが確認済み(レビュー結果報告書8.2章)。
- tester側では、この回帰確認として(a) pytest 149件(イテレーション1分127件を含む)・Vitest 37件(同26件を含む)が全件成功していることを参照確認し、(b) 追加で、インデックス追加対象の3カラムに関連するF-01(請求書発行・発行日)・F-03(見積書作成・発行日)・F-05(入金登録・入金日)の主要APIを実機で1件ずつ再実行し、応答内容・ステータスコードがイテレーション1テスト結果報告書の合格時と同一であることを確認する(実施結果は`テスト結果報告書.md`のTC-D14を参照)。
- F-01〜F-06・共通機能のテストケース自体(TC-C01〜TC-N02)は、詳細設計書・実装コードに変更がないため再実施せず、イテレーション1版の合格結果を踏襲する。
