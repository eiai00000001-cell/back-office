## 3. テスト観点

| # | 観点 | 定義 |
|---|---|---|
| 1 | 機能テスト | 詳細設計書の画面詳細設計・処理フロー・API/インターフェース設計どおりに動作するか(機能ID単位) |
| 2 | 異常系・入力値検証 | エラーハンドリング設計(詳細設計書8章)どおりに異常系が処理されるか |

| 5 | 機能横断・結合確認 | 複数機能にまたがる画面遷移・データの受け渡し等、単体テスト・機能単位レビューでは見えない不整合がないか(F-03→F-04→F-01→F-05の一連の業務フロー、ホーム画面のサマリー算出とF-05判定ロジックの整合等) |

### 3.1 機能ID単位の適用方針

- **F-08(案件・プロジェクト管理、イテレーション3・段階1追加)**: 観点1・2(詳細設計書4.9章の入力検証・422/404、納期状態の境界値)・3(削除時の`project_id`のNULL化と書類・入金・明細の残存、`ON DELETE SET NULL`、集計値のDB突合)・4(4.13.2チェックリストを旧コードとの応答比較で確認)・5(案件×F-01/F-02/F-03/F-04/F-05/F-07のデータ受け渡し、SC-03・05・07・13〜15の画面遷移)を全て適用する。特に4.9.5の「通常PUTで`project_id`を省略するとnullで更新される」挙動は設計どおりであることを実機で確認し、フロントエンドが編集時に現在値を送ること(画面テスト)を併せて確認する。
- **起動時マイグレーション自動適用**: 観点2(失敗時の停止・案内)・3(適用前後のデータ不変)を適用し、旧スキーマDBのコピーへの適用、冪等性、`alembic_version`無しDB(構造一致/不一致)、upgrade失敗、破損DB、二重起動、古いロックの回復、Uvicorn起動失敗を、使い捨て環境で実機確認する。

- F-01〜F-06および共通機能それぞれについて、観点1(機能テスト)・観点2(異常系)を基本の適用対象とする(イテレーション1で適用済み、方針変更なし)。
- F-01・F-02・F-03の金額計算はDB保存値の検算(観点3)を必須とする。
- F-04(見積→請求変換)・F-05(入金・売掛金管理)・F-06(ホーム画面サマリー)は、他機能のデータに依存して算出される派生値が多いため、観点5(結合確認)を重点的に適用する。
- 起動.app/終了.appは、単体スクリプト実行(developer済み確認)に加えて実際の`.app`バンドル起動(観点1・5)を重点的に確認する。
- **F-07(財務ダッシュボード、イテレーション2追加)**: 読み取り専用機能で、書き込み系の異常系(バリデーションエラー等)を持たないため、観点2は「区画ごとのAPI障害時のエラー表示分離」(詳細設計書4.8.6章)・「見積成約率0件時のnull返却」(4.8.5章)の2点に限定して適用する。F-01(売上)・F-02(経費)・F-03/F-04(見積・変換)・F-05(入金)の既存データを月次集計する性質上、複数機能のデータが単一画面に統合される典型的な結合確認(観点5)機能であるため、観点5を最重点で適用する。観点3(データ整合性)は、DB上の生データとAPIレスポンスの集計値の突合(発生主義での計上基準・0円/0件補完・除外条件)を重点確認する。

### 4.2 合否判定基準

- 期待結果(テストケース.mdに記載)と実施結果が一致した場合を「合格」とする。
- 詳細設計書・機能仕様書に明記された仕様との不一致、または実行時エラー・データ不整合が確認された場合を「不合格」とし、再現手順・実際の結果を記録する。
- README.md「6. 詳細設計書との差異」に記載済みの差異は仕様確定事項として扱い、原則不合格としない。ただしその差異どおりに実際に動作しているかは実機確認する。
- テスト実施中に、詳細設計書とmockupsとの間、または詳細設計書内の章同士の間で軽微な記載の不整合が見つかった場合(実装への影響がないもの)は「要確認事項」として記録し、不合格扱いとはしない。
- 実機確認の手段がない項目は「未実施」とし、代替として実施した静的確認・参照確認の内容を明記する。

### 4.3 F-07向けの追加方針(境界値・実データ検証)

- 詳細設計書4.8章の集計ロジックは、SQLの`WHERE`句による日付範囲絞り込みと`strftime`による月グルーピングを組み合わせているため、期間境界(`date_from`前日のデータが正しく除外されるか)を境界値テストとして重点確認する。
- F-04(見積→請求変換)直後で`issue_date`がNULLの請求書(詳細設計書4.4章)が、F-07の月次売上集計から正しく除外されることを、実際にF-04変換を経由したデータで確認する(F-04とF-07の結合確認)。
- 見積成約率(4.8.5章)は、0件時のnull返却(0除算回避)に加え、変換済み・未変換が混在するケースでの按分計算(小数第1位以下の丸め表示)も実データで確認する。
- 損益(収支)の黒字/赤字視覚化(基本設計書4.13章)は、赤字月を意図的に作成し、実際に配色が切り替わることをスクリーンショットで確認する。

### 4.5 イテレーション3・段階1の追加方針

- 不具合が見つかった場合はコード修正は行わず、重大度(高/中/低)と再現手順を記録する。重大度の目安: 高=既存または新規の主要な業務操作が画面から実行できない・データが失われる、中=業務に支障はあるが回避手段がある・誤表示、低=異常入力時の挙動不備など影響が限定的。
- 既存機能に起因する不具合でも、今回の確認で見つかった場合は不合格として記録し、起因が過去イテレーションである旨を明記する。
- 使い捨て環境(スクラッチパッド内のコード複製・DBコピー・スタブ)の後片付けは実施せず、結果報告書で場所を報告する。

### 4.6 フォローアップ(不具合#1・#2修正・エラーメッセージ日本語化の再確認)の追加方針

- 対象: TC-J19(ID範囲)・TC-UI15(既存書類の保存)の再実施、および新規TC-J21・TC-J22・TC-UI20・TC-RG11。tester自身が実機で再実行し、developerの自己申告は用いない。
- 実施環境: 実DB(`db/back_office.db`)に触れず、スクラッチパッド内の使い捨てDB・別ポート(8003〜8005)で実施する。フロントエンドは修正後の`frontend/src`を`vite build --outDir`でスクラッチパッドへ出力し(`backend/static`は変更しない)、Playwright(Chromium、ヘッドレス)で画面操作する。ファイルの削除は行わない。
- 型不正(列挙値・日付型・JSON構文)が英語のまま残る点は、詳細設計書8.1章の既知の制約のため不合格とせず記録する。
- 修正確認フロー: 不具合#1・#2とも、今回の修正は既にreviewerの再レビュー(レビュー結果報告書9.9節)を経ているため、本フォローアップはtester再確認の段階に当たる。
