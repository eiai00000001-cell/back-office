## 2. プロジェクト概要

### 2.1 クライアント情報

- EIAI TEC(個人事業主本人)。本システムはEIAI TEC本人が自身の事務作業のために利用する、自分専用のツールである(企画書1.3、プロジェクト計画書2.1)。

### 2.2 プロジェクトタイプ

- 個人事業向け業務システムの新規開発(ローカル完結型)。
- 全体構想(企画書の計15機能)を段階的なイテレーションに分けて開発する方針であり、本書は初回イテレーションを対象とする(プロジェクト計画書2.2、4.1)。

## 3. 背景・目的

- EIAI TECの個人事業における請求書発行・経費管理・見積書作成・財務管理・確定申告対応・契約書管理・経営管理など、複数の事務業務をホーム画面から選択して行える形に一元管理したいという要望が出発点である(企画書1.1、プロジェクト計画書2.2)。
- 本システムはEIAI TECの「ポートフォリオ=業務基盤」戦略の中核ツールと位置づけられており、実業務での利用に加え、AI駆動開発の実績としてGitHub公開も想定されている(企画書1.2、プロジェクト計画書2.2)。
- 初回イテレーションでは、「お金の流れを止めない・管理する」ための中核機能(請求書発行・経費管理・見積書作成・見積→請求変換・入金/売掛金管理)を確実に使える状態にすることを目指す(プロジェクト計画書3章)。

## 4. 用語集(クライアント目線)

| 用語 | 説明 |
|---|---|
| 請求書 | 取引先に対して、提供した商品・サービスの対価の支払いを求めるための書類。 |
| 見積書 | 取引先に対して、提供予定の商品・サービスの想定金額をあらかじめ提示するための書類。 |
| 経費 | 事業を行う上で発生した支出(交通費、通信費、消耗品費など)。 |
| 勘定科目 | 経費や取引の内容を分類するための項目名(例: 旅費交通費、通信費など)。 |
| 消費税(標準税率) | 商品・サービスに課される税金。制度上は標準10%・軽減8%の税率区分があるが、EIAI TECの事業では軽減税率対象の取引が発生しないため、本システムでは標準10%(および非課税・不課税)のみを扱う(10章★3で確定)。 |
| インボイス制度(適格請求書等保存方式) | 2023年10月開始の制度。要件を満たした「適格請求書」を発行することで、取引先が消費税の仕入税額控除を受けられる仕組み。本システムでの対応方針は正式に登録・運用するかは未定だが、将来の対応に備え、請求書に登録番号欄をレイアウト上用意しておく(記載は必須としない。10章★1で確定)。 |
| 適格請求書発行事業者登録番号 | インボイス制度に対応する事業者が税務署から付与される登録番号(T+13桁)。請求書に記載欄を設けるが、記載は任意とする。 |
| 売掛金 | 商品・サービスを提供したがまだ代金を受け取っていない金額(未回収の請求金額)。 |
| 入金消込 | 入金があった請求書について、入金済みであることを記録・反映する作業。 |
| 取引先 | 請求書・見積書の発行先となる顧客・企業。 |
| ホーム画面 | システム起動後に最初に表示される、各機能への入口となる画面。 |
| ローカル完結 | インターネット上のクラウドサービスを使わず、EIAI TEC本人のPC内だけでデータを保存・処理すること。 |

## 5. スコープ

### 5.1 フェーズ1(今回対象)

企画書のTier1に分類された5機能のうち、以下5機能とそれを利用するための最小限のホーム画面・共通UIを対象とする(プロジェクト計画書5.1)。

1. 請求書発行(最優先)
2. 経費管理(最優先)
3. 見積書作成(次点)
4. 見積→請求の自動変換(次点)
5. 入金・売掛金管理(次点)
6. ホーム画面・共通UI(上記5機能への導線。企画書1.1「ホーム画面から選択して行える形」に対応する必要最小限の範囲)

技術スタック(Python+React+SQLiteによるローカル完結環境)の構築は、上記機能を動かすための基盤として本イテレーションのスコープに含む(プロジェクト計画書5.1)。

各機能の詳細要件は6章、詳細仕様は`機能仕様書.md`を参照。

### 5.2 フェーズ2以降(対象外)

以下は今回のイテレーションでは対象外とし、将来イテレーションで扱う(プロジェクト計画書5.2)。

- Tier2: 財務ダッシュボード、経営管理、案件・プロジェクト管理、リマインダー/通知、レポート出力
- Tier3: 確定申告対応、契約書テンプレート、顧客管理(簡易CRM)、レシート/領収書OCR取込
- 横断機能: データバックアップ/エクスポート
- マルチユーザー対応・外部公開を前提としたアカウント管理や権限設計(EIAI TEC本人専用利用のため実施しない)

## 6. 機能要件

各機能要件の詳細な入力項目・処理・データ項目は`機能仕様書.md`で定義する。本章では業務要件レベルで整理する。

なお、初版(1.0)では企画書・プロジェクト計画書に明記のない事項(税率端数処理・勘定科目一覧・アラートの実現範囲など)をanalystが暫定的に補い、10章「要確認事項・未解決事項」として整理していたが、2026-09-15実施のEIAI TEC本人へのヒアリングにより★1〜★11のすべてが確定した。本改訂(1.1)では確定内容を本章・7章・8章に反映済みである。詳細な確定内容・経緯は10章を参照。

### 6.1 F-01 請求書発行

- 取引先ごとに請求書を作成できる。
- 発行日・支払期限・品目明細(品目名・数量・単価・税区分)を入力し、消費税額・合計金額を自動計算できる。消費税額の端数は切り捨てで計算する(10章★2で確定)。
- 税区分は標準税率10%・非課税・不課税のみを扱う(軽減税率8%は取り扱わない。10章★3で確定)。
- 請求書番号は自動で採番される。
- 作成した請求書はPDFとして出力できる。
- インボイス制度(適格請求書)への対応方針は未定だが、将来の対応に備え、登録番号欄をレイアウト上用意する。記載は必須としない(10章★1で確定)。

### 6.2 F-02 経費管理

- 発生日・勘定科目・金額・税区分・支払先・支払方法・メモを入力して経費を記録できる。勘定科目は機能仕様書に定める標準科目リスト(青色申告向け)を用いる(10章★4で確定)。
- 記録した経費を一覧表示・検索・絞り込みできる。
- 勘定科目別・期間別に金額を集計して確認できる。
- 領収書の画像・PDFファイルを経費記録に添付できる(自動読み取り(OCR)は対象外。手動添付とする)。本機能は初回スコープに正式に含める(10章★5で確定)。

### 6.3 F-03 見積書作成

- 取引先ごとに見積書を作成できる。
- 発行日・有効期限・品目明細(品目名・数量・単価・税区分)を入力し、消費税額・合計金額を自動計算できる。
- 見積書番号は自動で採番される。
- 作成した見積書はPDFとして出力できる。
- 見積書の状態は「作成中」「確定」のシンプルな2区分で管理できる(提出済み・承認・却下等の詳細なワークフローは持たない。10章★7で確定)。

### 6.4 F-04 見積→請求の自動変換

- 作成済みの見積書から、その内容(取引先情報・品目明細・税区分)を引き継いだ請求書を作成できる。
- 変換後の請求書は、請求書番号を新規に採番し、発行日・支払期限などを改めて入力・編集できる。
- 変換後の請求書と変換元の見積書はそれぞれ個別に編集でき、一方を編集しても他方には自動反映されない。
- 本イテレーションでは、1件の見積書につき1件の請求書を作成する対応関係(1対1)とする(10章★8で確定)。なお、将来イテレーションで分割請求・部分請求(1件の見積書から複数の請求書を作成する対応)への拡張を希望する要望があるため、データモデル設計上の配慮については7章非機能要件を参照。

### 6.5 F-05 入金・売掛金管理

- 発行済みの請求書ごとに入金状況(未入金・一部入金・入金済み)を記録・確認できる。
- 入金日・入金額を記録できる。
- 支払期限を過ぎても入金が確認できていない請求書を、一覧上で分かりやすく(強調表示等で)確認できる。
- 「未入金/支払遅延のアラート」は、画面上での一覧表示・強調表示による確認機能とし、メール送信やデスクトップ通知などのプッシュ型通知は含まない(Tier2のリマインダー/通知機能は対象外のため。10章★6で確定)。

### 6.6 F-06 ホーム画面・共通UI

- システム起動後、上記5機能(F-01〜F-05)へ画面上のメニューやカードから移動できる。
- 未入金件数・支払期限超過件数など、業務上把握しておきたい簡易な状況をホーム画面上で確認できる。
- 詳細な集計・グラフ表示(財務ダッシュボード相当)は対象外とし、将来イテレーションで検討する。

## 7. 非機能要件

- データ保存はEIAI TEC本人のPC上のSQLiteファイルに行い、外部クラウドサービスとの同期は行わない(プロジェクト計画書6章)。
- 想定利用者はEIAI TEC本人のみであり、他者との共同利用・外部提供は想定しない(プロジェクト計画書6章)。
- バックエンドはPython、フロントエンドはReact、ローカルDBはSQLiteを使用する(プロジェクト計画書6章、技術スタック確定済み)。
- 単一ユーザー・小規模データ量を前提とし、大量データ処理を想定した性能要件は設けない。
- 外部への公開を行わないため、外部からの不正アクセス対策の優先度は低いが、取引先情報・経費の支払先情報など第三者の情報を含むため、ローカルファイルとしての取り扱いには留意する。
- ログイン認証機能は実装しない(認証なし。ローカル環境でEIAI TEC本人のみがアクセスする前提)(10章★9で確定)。
- 将来のTier2・Tier3機能追加を見据え、データモデル・画面構成に一定の拡張余地を持たせる(プロジェクト計画書7章)。
- 見積→請求変換(F-04)は本イテレーションでは1対1の対応関係に固定して実装するが、将来イテレーションで分割請求・部分請求(1対多)への拡張を予定していることを踏まえ、データモデル設計において当該拡張が大きな手戻りなく行えるよう配慮する(例: 請求書側から見積書を参照する構造とし、見積書側に固定的な1対1制約を持たせない設計とする等、具体的な設計方針は設計フェーズ(architecture)で検討する)(10章★8で確定)。
- データバックアップ/エクスポート機能は本イテレーションの対象外である。対象外期間中のデータ保全は、EIAI TEC本人がSQLiteファイルを手動で定期的にコピーする運用でカバーする方針とし、システム側での対応は行わない(バックアップ/エクスポート機能自体は将来イテレーションで別途検討する)(10章★11で確定)。

## 8. 制約条件

- 予算: 特に制約なし(EIAI TEC本人自身による開発のため、金銭的な予算制約は設けない)(10章★10で確定)。超過時の対応方針についても、予算制約自体がないため現時点では定める必要がない。
- 納期: 外部クライアント向けの納期制約はなく、EIAI TEC本人のペースで進める(プロジェクト計画書4.3、6章)。具体的な期日・マイルストーンの指定はない。
- 体制: 計画→要件定義→設計→実装→テスト→納品の各フェーズを専任サブエージェントが担当する開発フローに沿って進行する(プロジェクト計画書6章)。
- 技術スタック: Python(バックエンド)+React(フロントエンド)+SQLite(ローカルDB)で確定済み(プロジェクト計画書6章)。

---

## 9. 前提条件

- 利用者はEIAI TEC本人のみであり、マルチユーザー対応・アカウント管理・権限設計は行わない(プロジェクト計画書5.2、6章)。
- データはローカル完結とし、クラウド同期は行わない(プロジェクト計画書6章)。
- 本イテレーションはシステムの新規構築であり、既存の請求書・経費データ等を他システムから移行する作業は本書のスコープに含まない(一次情報に記載なし。移行要否は要確認とはせず、記載がないため対象外として扱う)。
- 実行環境(ローカルでの起動方式・パッケージング方法等、Pythonサーバーの起動やReactアプリの配信方法)の具体的な方式は、本書では定めず設計フェーズ(architecture)で具体化する。
